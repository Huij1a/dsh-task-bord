# 19 步出题流水线

每道题一个目录，19 份提示词冻结，节点之间只通过文件交接；12 冻结后，13 只在项目外独立题包内读取最终题面和 A 系列附件，与专家侧产物分开。项目门槛、平台字段和行业约束均从当期规范解析到 `artifacts/00_spec/项目门槛.json`，不能沿用另一期的固定值。

## 开工前先读

项目根的 `AGENTS.md`（DSH 自动加载）、`docs/进度.md`、`docs/问题登记表.md`，以及本期项目规范。

## 目录结构

```text
tasks/<题ID>/
  manifest.json        冻结文件清单、版本、规范路径与 industry
  prompts/00_spec.md … 18_submit.md
  workflow.js          编排脚本
  artifacts/00_spec/   项目门槛.json、规范摘录.md
  artifacts/01_src/ … 18_submit/
  artifacts/13_answer/<runId>/  评分后由 judge 原子归档的答卷

D:\高经作答区\<taskId>\<runId>/
  input/              冻结最终题面和白名单 A 附件
  output/             13 的交付物与自报运行记录
  host_trace.json     host 生成的唯一运行指标真源
```

## 怎么跑

1. 用插件开题，不手工复制 `tasks/T-demo/`：

```text
authoring_init(
  industry="<L1 或 L1/L2 行业>",
  specPath="<当期规范文件或目录>"
)
```

返回 `taskDir`、冻结版本和 `next`。`authoring_init` 会自动复制母版、计算 manifest，不需要手工建目录或重算哈希。

2. 用 `authoring_script(taskId, kind="batch", batch="A")` 取当前编排脚本原文及参数说明。提交给 `workflow` 时，`args` 必含四项：

```json
{
  "taskDir": "<authoring_init 返回的绝对路径>",
  "batch": "A",
  "specPath": "<当期规范文件或目录>",
  "industry": "<L1 或 L1/L2 行业>"
}
```

3. 按四批顺序运行。上一批产物和判定检查通过后再续下一批；插件返回的 `next` 可用于确认下一批参数：

| 批次 | 节点 | 批次闸门 |
|---|---|---|
| A | 00_spec + 01–07 | 先解析项目门槛；07 只按本批 06 产物及规范判定 |
| B | 08–12 | 08/11 读 00_spec 与 04 的唯一真源；10/12 按当期门槛 |
| C | 13–16 | 13 在项目外题包作答；14 生成 host trace/隔离审计、逐卷评分并按条件补跑；16 消费冻结门槛与分卷结论 |
| D | 17–18 | 16 通过才打包；18 按字段清单动态映射并重建上传包 |

不要改写脚本中的节点顺序和返修条件。workflow 不能暂停续跑，所以批次边界就是恢复点；失败只重跑当前批。

## A/B/C/D 的边界

- **A = 00_spec + 01–07**：解析项目规范，完成素材、脱敏、定位、证据、附件制造和元数据检查。规范未写的门槛保留 `null`，不要补默认值。
- **B = 08–12**：生成题面、诊断难度、产出标答与作答思路、冻结版本。04 的 `交付规格.json` 是交付结构唯一真源。
- **C = 13–16**：13 只读项目外题包 `D:\高经作答区\<taskId>\<runId>\input`、只写同包 `output`，并写自报 `运行记录.json`。14 先用 `authoring_isolate` 生成题包 `host_trace.json` 和分卷 `隔离审计.json`，再每卷只调用一次冻结 `judge.py --copy-to`。默认 `C01`；仅近线分/轮次或时长近下界/首卷无效时补一次 `C02`。15 逐卷读卷；16 只做入包前结构检查并输出唯一 `结论.json`。
- **D = 17–18**：17 只按显式白名单打包，仅模型输入包只含题面+A 系列，排除 B 系列、rubric、门槛、提示词、脚本、日志、答卷和运行记录；18 按字段清单生成映射，并在此后重建上传包。

## 返修环

返修条件与阈值全部按 `artifacts/00_spec/项目门槛.json` 和节点判定文件执行，不固定为标准分或标准百分比：

- 07 不通过 → 按 findings 回 06 修，复检最多 2 次。
- 10 不通过 → 只按诊断中的可执行路由回 05 或 08，最多 2 次；不在本节点改门槛，也不自动回 11。
- 14 未通过 → 停在评分报告，由人决定是否返修；不自动改 11，不默认任何固定分数线。
- 16 不通过 → 停止当前批次；阻断项未清零前禁止进入 17 打包，不自动返修 11。

## 硬规则

- 每题独立目录，prompts 只读；节点执行前校验 manifest 哈希，不一致拒绝执行。
- 节点之间不共享会话上下文，只读上游产物文件。
- 判定节点只读不写；16 无法确认上游结论时必须报缺证据，不能自行补判。
- 不跨 `industry_tree`，不违反 `forbidden`；跨题差异或去重约束只按当期规范执行，规范未声明时不得自行发明数量或比例。
- 13 不读取题包 `input/`、`output/` 以外的项目材料，不在题包外写作答产物；14 的隔离审计发现越界读取即判该卷 invalid。
- 运行时长和轮次以 host 生成的 `host_trace.json` 为唯一真源；13 的 `运行记录.json` 只作一致性核对，不得替代宿主 trace。

## 每批结束检查

1. 用 `authoring_status` 看本批产物数量、项目门槛摘要和判定结论。
2. 对 A 批确认 00_spec、07；对 B 批确认 10、12；对 C 批确认 14、16；对 D 批确认 17 `核对.json` 和 18 字段计数。
3. 批次通过后再提交下一批；失败只重跑该批。
4. 最后向用户报告走到哪一批、哪些通过、哪些未验证；全量未实际跑通时不要声称可用。
