2. **17 上传包内 `${SID}` 草案与 18 终稿的字节一致性**：构建器只在 stub 层校验“只替换一个成员 + 成员集合不变”；真实 xlsx/docx 压缩格式（`deflate`/时间戳/外部属性）需实跑确认成员 bytes 重算稳定，必要时在 17 生成时固定 zip 元数据。
3. **`18_rebuild_upload` 是编排内联 brief 无独立提示词**：它的文案跟随 workflow 版本变化，不是可独立改的提示词；若未来要单独审查，需再抽成 `19_rebuild.md`（本卡按 Lead 裁决不改节点数）。
4. **05 `source_locator.source_ids` 与 02 `脱敏映射.json` 的强绑定**：若 02 输出被人工修改而不同步 05，05 audit 会 fail；这是有意 fail closed，但实跑时需一次通过。
5. **07/09 finding_id 只是命名契约**：06 repair 的逐条闭环仍靠 audit 的 `findings_closed` 计数，真实 07 是否会稳定给同一 finding 同一 ID 未验证。
6. **`_v006_manifest_check.py` 版本升级为 v008 后**，旧 v007 任务副本 `authoring_verify(against="template")` 会判不一致，需按新母版重开题。
7. 插件未改：若后续改插件，必须重新 `node --check` + smoke，并把 `index.js/README.md/package.json` 同步到 desktop profile 后核对 sha256。

## 5. 实跑 A 批操作步骤

前置：本期项目规范文件或目录已就位（例如 `D:\<规范目录>`），确认没有同名 `tasks\<taskId>`。

1. **开题（插件工具）**
   ```text
   authoring_init(industry="<L1 或 L1/L2 行业>", specPath="<当期规范文件或目录>")
   ```
   - 可选 `taskId`（字母数字、`-`、`_`，2–64 字符；省略自动 `T-YYYYMMDD-NN`）。
   - 成功返回 `taskDir`（`<root>/tasks/<taskId>`）；失败常见原因：题目录已存在、manifest 与母版不一致。
2. **取脚本与参数（插件工具）**
   ```text
   authoring_script(taskId="<taskId>", kind="batch")
   ```
   - 返回当前 `workflow.js` 原文 + `taskDir/batch/specPath/industry` 参数；**原样提交，不要让模型改写脚本**。
3. **提交 workflow（A 批）**
   ```json
   {
     "taskDir": "<authoring_init 返回的绝对路径>",
     "batch": "A",
     "specPath": "<当期规范文件或目录>",
     "industry": "<L1 或 L1/L2 行业>"
   }
   ```
   - A 批节点：`00_spec → 01_src → 02_scrub → 03_survey → 04_scope → 05_evidence → 06_build → 07_metacheck`。
   - 正常路径 9 次 agent 调用；07 失败最多 2 次回 06 repair。
   - 通过标准：`GATE_A` 满足，`00_spec/项目门槛.json`、01 三产物、02 五产物（含 `脱敏映射.json`）、05 七产物、06 attachments + `返修记录.json`（若 repair）、07 `result.json` 均落盘且过 audit。
4. **检查点**
   ```text
   authoring_status(taskId="<taskId>")
   ```
   看 A 批产物、项目门槛与判定结论；通过后 `next` 给 B 批信息，再执行 `authoring_script(kind="batch")` → workflow `batch="B"`。
5. **失败处理**
   - 任何 gate/audit fail：只重跑当前批，不手工打补丁续跑；先看 workflow 返回的 `error`（`workflow: <node> machine audit failed: ...`）定位节点。
   - 旧任务不要补丁继续跑；用新母版重开题。

## 6. 建议的首轮 A 批观察点

1. `00_spec` 是否把平台字段/业务字段分域，`project_threshold.json` 的 `extraction_status` 是否正确。
2. 01 是否真的抓到原文（不是摘要），`原文摘录/<SID>.md` 元数据块与磁盘 sha 是否一致。
3. 02 每个来源是否都有脱敏副本，`脱敏映射.json` 的 `summary.blocked` 是否为 0。

5. 06 首次 `initial` 是否 `findings_total=0`；若 07 fail 引发 repair，`返修记录.json` 的 `unrelated_files_unchanged` 是否 true。
6. 07 `result.json` findings 是否都带 `finding_id`。
